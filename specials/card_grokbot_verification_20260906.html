3/12
第一原則

AI 最佳角色是結對夥伴，不是代寫機，更不是把自己的判斷整包外包

00:00–01:24Lauren 先反對「為了顯得懂 AI，就追求一週送出 100 個自己都不理解的 PR」。AI 省下打字時間，卻可能把成本轉成更重的審查、除錯與重工。
真正的效率式淨產出＝生成速度 − 審查時間 − 重工成本 − 上線後風險。只算生成量，會把品質債誤認為生產力。
陷阱：「Vibe code 到營收」是她拿來批判的壓力敘事，不是她鼓勵的成功公式。
做法：先保留人的問題定義、架構品味與風險判斷；把可重複執行、可驗證的工作交給 Agent。
4/12
信任曲線

你不信任一個 Agent，就不可能放心擴到一百個；規模化之前，要先讓「完成」變成能被證明的狀態

01:24–06:05她把管理工程師的經驗套到 Agent：沒有信任時，人會微管理、逐字看輸出，並成為所有任務的單點瓶頸。過去五個月，她逐步從幾個本機 Agent，走到部分 PR 可自動合併。
成熟度階梯
  1. 人逐步提示、逐步驗收。
  2. Agent 能自己跑測試與產品流程。
  3. 把常見失敗寫成 skills 與 evals。
  4. 用 CI、型別與架構做硬限制。
  5. 再擴到雲端並行；自動合併是最後一階，不是起點。
單晚約 20 個 PR 已合併，是 Lauren 的工作情境自述，不代表所有團隊都適合直接複製。
5/12
驗證閉環

Verification 不是再叫模型「檢查一次」，而是讓它操作真正的程式、觀察結果、失敗後自己修正

“The most important skill … is verification.”（06:06）
她給的驗證例子
  • 真的執行程式與使用者流程。
  • 抓 CPU trace、heap snapshot。
  • 開啟 iOS 模擬器或 Electron／Web UI。
  • 讀取 console、畫面、效能與穩定性證據。
“You are the verifier … you’re the bottleneck.”（08:52）
完成定義：不是「程式碼已生成」，而是「指定情境在真實執行環境通過，且留下可重查證據」。
6/12
Control Glass／Feature Map

工具只能讓 Agent 看見畫面；Feature Map 才告訴它產品裡每個功能在哪裡、如何抵達與如何驗證

07:19–13:30Lauren 為 Cursor 的 Agent 視窗建立控制技能，讓 Agent 能啟動開發版、操作 UI、抓 trace；但它仍不知道「左側欄」「PR 分頁」對應到哪段程式。因此再加 Feature Map，記錄功能、導航路徑、快捷鍵與可選取的 DOM 屬性。
功能地圖的價值即使回報只有一張截圖和三個問號，Agent 也能把模糊症狀映射到功能位置、重現路徑及相關程式碼，而不是在整個 repo 裡亂猜。
維護成本：產品變動後地圖會過期，所以 pstack 同時提供建立與維護驗證技能的流程。
7/12
pstack／Skills／Evals

每次看到 Agent 以固定方式犯錯，就把教訓變成 skill；再用 eval 當「Agent 的單元測試」

13:41–23:23pstack 不是一開始就完整設計的框架，而是從 Control Glass、HAL 等技能逐步長出來。Skill 用 Markdown 編碼任務知識、工具路徑與判斷方式；Eval 則檢查 skill 是否真的改變行為。
她的 eval 做法
  1. 協調 Agent 先寫評分規準。
  2. 多個子 Agent 在獨立、刻意不標示「考場」的目錄執行。
  3. 用另一種模型當 judge，降低同模型自評偏差。
  4. 以 `/loop` 反覆修正，直到評分門檻達標。
官方 Cursor plugin repo 可查到 pstack，作者標示為 Lauren Tan；公開版名稱是 `/poteto-mode`。
查證：Cursor 官方 pstack 原始碼與文件
8/12
從本機到雲端

最安全的擴張路徑：先本機觀察，再雲端委派，最後才考慮自動合併

24:00–28:42
  1. 本機：直接看 Agent 怎麼啟動程式、呼叫工具與判讀錯誤。
  2. 可重現：驗證流程穩定後，把環境與技能帶到 cloud agents。
  3. 自動化：讓錯誤回報主動觸發重現與修復。
  4. 放權：只有硬性品質門通過，才逐步提高並行與合併權限。
Lauren 的明確警告：還在微管理階段就直接開數百或數千個 Agent，只會大量浪費 token，並把錯誤同步放大。
9/12
Benny 案例

高價值自動化不是「修好了」三個字，而是自動重現、比較版本，告訴你問題究竟還在不在

25:15–26:38Benny 會接收錯誤回報，在雲端電腦啟動 Cursor，利用同一套控制與驗證技能操作產品。影片案例裡，它確認舊版本可重現、main 已無問題，最後判定只差發布新版。
一份可用交付應包含
  • 原始回報與重現條件。
  • 失敗版本的畫面、log 或 trace。
  • 候選修正版本同一路徑的對照證據。
  • 剩餘動作與責任人。
關鍵：Agent 回報的是可查證狀態，不是要求人相信它的語氣。
10/12
Dune／硬性工程邊界

Prompt 與規則會被忘記；真正可擴張的底座，是讓錯誤做法在型別、架構或 CI 階段直接失敗

29:33–47:07Dune 是 Lauren 為 Grok Bot client 建立的內部、工作名稱架構，可類比為「給 Electron app 用、且為 Agent 設計的 Next.js」。它讓功能共置、最短路徑同時成為正確路徑，並用依賴邊界與靜態檢查防止 Agent 走捷徑。
由硬到軟的防線
  1. 架構與型別系統。
  2. 編譯器、靜態分析、lint、依賴圖與 CI。
  3. BugBot 自動審查。
  4. Rules、skills、style guide。
  5. 最後才是人工 code review。
影片提到在此專案禁用 `useEffect` 與一般 code comments，是針對該 codebase 的防呆選擇，不是所有 React 專案都該照抄的全球規則。
判準：同一個錯誤若需要人在 PR 留言第二次，就應思考能否改成 lint、CI、型別或架構上根本不可能發生。
11/12
數字、成本與適用邊界

她的成果很強，但最值得複製的是投資順序，不是 PR 數量

影片數字證據類型不能直接推論
投影片：5 個月超過 3,000 PR本人投影片未經 repo 級第三方稽核。
上月約 1,000 PR；本月 12 日前近 800本人自述不等於每個 PR 都有同樣規模、品質或商業價值。
單晚約 20 PR 自動合併本人自述不等於一般 repo 應立即開啟 auto-merge。
約 600 PR 重構 Grok Bot本人自述不證明大重寫必然勝過漸進修改。
PR 約 50～1,000 行，無硬上限口頭範圍不是正式統計平均值。
成本邊界：Lauren 明說自己身處有大量 token 的 AI 團隊；一般人應先算重構、eval、雲端環境與長期維護的 ROI。
SpaceXAI 官方目前列 Grok 4.6 API 基礎價格為每百萬 input token 2 美元、output token 6 美元；影片中「與 4.5 同價」是講者帶保留語氣的現場說法。
12/12
可執行藍圖

不要先買一支 Agent 大軍；先把一條工作流做到「不用靠相信」

現在做

  • 挑一個小而真實的任務。
  • 寫清楚完成條件與不可碰範圍。
  • 讓 Agent 跑真實產品路徑。
  • 保留畫面、log、hash 或測試結果。

接著固化

  • 把重複失敗變成 skill。
  • 替 skill 建 eval。
  • 能機械判定的規則移進 CI。
  • 持續維護 Feature Map。

最後放大

  • 獨立任務才並行。
  • 每個工作者隔離環境。
  • 高風險動作保留授權門。
  • 通過真實驗證才發布或合併。
一句話結論：多 Agent 的瓶頸不是模型數量，而是你有沒有把「品質」翻成 Agent 能執行、系統能阻擋、第三方能重查的證據。
